# 接手实现的技术基础

本文是接口契约与拆分方案，不是已经接入的运行时代码。先保留现有发布版本，按阶段迁移，不要把全部功能塞进现有 Combat.tick。

## 先解决的现有结构限制

| 代码位置 | 当前事实 | 扩展前的处理 |
|---|---|---|
| Combat.java | 一个 UUID 对应一个 Strike；位移、命中、终结、成就在同一类 | 单独保留 LegacyIaido 执行器，用测试固定原参数；再增加新招式执行器 |
| Combat.java sweep | 突进路径的扩张 AABB + 遮挡检测 | 保留旧招式判定；新左右斩单独用扇区/扫掠体判定，不能把范围查询直接当成刀刃触碰 |
| Combat.java tick | 固定 MAIN_HAND swing；Strike 不记录起手槽位/手别 | 新动作记录主副手、物品身份和提交时点，扣正确那把刀的耐久 |
| TachiItem.java | 旧招式冷却与消耗在 releaseUsing 中提交 | 原流程原数值保留；新招式独立冷却，不为旧居合新增剑意门槛 |
| SlashPayload.java | 只有 owner/origin/yaw/charge/kind；没有动作唯一编号、开始 tick 或取消消息 | 增加版本化的新协议，旧 slash 先作为兼容入口，禁止仅换字段却沿用旧解码器 |
| OborokageClient.java | Scene 从收到包时 age=0 开始；sceneAge 查第一个匹配玩家的 Scene | 每位玩家以最新动作 ID 为准；服务器起始时刻同步，避免上一段残留动画干扰下一段 |
| OborokageClient.java | 旧客户端演出 48 tick，服务端满蓄力动作约 38 tick 结束 | 分开定义攻击有效期与视觉收势期，后者不能阻止新的合法旧居合 |
| HandsMixin / IaidoPoseMixin | 单刀姿态直接修改左右臂；没有独立副手时间轴 | 按物理左右手映射动作轨，处理左利手，避免双手套用同一轨道 |
| SheathModelMixin | 根据单场景 age 替换模型，没有两把刀独立出鞘状态 | 每把刀有渲染状态，刀鞘挂点独立于刀柄挂点；物品渲染副本不得写回真实 ItemStack |
| CameraMixin | 直接介入原版相机，依赖私有 zoom 方法 | 建立单一镜头控制器和恢复 token，检测其他相机模组冲突并可降级为原视角 |

## 建议模块

- `legacy/LegacyIaido`：封装现有单刀规则，不改变参数与终结语义。
- `combat/CombatSession`：单个玩家正在执行的动作、攻击窗口、输入缓冲、手别与资源提交状态。
- `combat/MoveDefinition`：招式定义（ID、各阶段 tick、移动规则、分段命中、可取消窗口、动画/FX ID）。
- `combat/InputRouter`：区分旧居合、新普通连击、架刀、影步与奥义，处理原版交互冲突。
- `combat/HitResolver`：新动作的扇区/扫掠查询、遮挡、队伍过滤、每段命中去重。
- `combat/ExecutionPolicy`：隔离旧强制终结；普通连击和反击使用正常伤害链。
- `combat/GuardController`：前向格挡、精准窗口、架势损耗、不可格挡类型白名单/黑名单。
- `combat/BladeIntent`：只影响新增玩法的剑意，收益上限与反刷规则。
- `progress/FeatTracker`：消费已结算战斗事件，为成就维护有限长度记录。
- `client/AnimationController`：左右臂/刀鞘/刀刃轨道与阶段插值。
- `client/CameraDirector`：只在本地处理镜头；保证恢复与中断。
- `client/BladeTrailRenderer`：按刀刃挂点轨迹生成刀光，另有世界空间命中表现。
- `network`：客户端请求、服务端动作开始/取消/阶段事件及配置能力握手。

不要先引入庞大外部动画库再猜测 26.3 支持性。当前骨骼 mixin 可以作为原型，但能否继续满足双刀动作与整合包兼容，需要实机判断。

## 状态机与数据契约

新动作状态：`IDLE → STARTUP → ACTIVE(window) → RECOVERY → IDLE`；蓄力、架刀另设可持续状态。取消必须进入明确定义的清理分支。
旧居合的输入、时序与冷却继续由旧规则支配；新连段/收势不得额外锁住旧居合。必要时旧居合请求取消新增动作，再按原有冷却接受或拒绝；已经发生的伤害不回滚，也不能重复提交新动作的资源。

最小会话字段：

```text
actorUUID, actionId, moveId, startServerTick, phase
mainHandSnapshot, offHandSnapshot, requiredEquipment
charge, lockedDirection, comboIndex, inputBufferExpiry
hitSets[hitWindowId], committedResourceWindows, intentAtStart
originDimension, cancelReason
```

`actionId` 是服务器分配的每次动作唯一序列；不要用招式 ID 代替动作 ID。
命中去重键为 `(actionId, hitWindowId, targetUUID)`。交叉斩若允许两段各命中一次，就有两个明确窗口；绝不是每 tick 各打一遍。Boss 多部件须合并到实际承伤实体身份。

客户端请求只发送 `requestSequence / requestedAction / inputPhase` 等意图；方向从服务器可信玩家状态推导并校验。客户端不能指定伤害、终结标志、命中实体列表或随意传入满剑意。
服务器检查：存活、维度、装备、槽位变更、冷却、已有动作、允许状态、请求频率与序列是否重复。主副手物品交换后如何处理在招式定义中规定；默认取消新动作的未执行窗口，已发生的伤害/耐久不重复结算。

服务端事件至少携带：`actionId / actor / moveId / startServerTick / direction / handedness / seed / phase`。取消事件携带 `actionId / reason`。旁观者只接收角色与特效事件，不能接收强制切镜头命令。
新加入追踪范围的客户端应得到当前动作快照；乱序、重复、过期事件丢弃，世界切换后清空。利用时钟偏移估计还原阶段，不把服务器绝对 tick 与本地世界 tick 直接相减。延迟过大可跳到当前姿态，不重新播放已完成伤害。

## 几个真正难的点

1. **动作与命中一致**：原版人物骨骼自由度有限，不能只拉长两只手臂。定义刀柄、刀尖、刀鞘、护手挂点；由共同的招式时间轴驱动服务端简化攻击体和客户端刀刃轨迹，分别验证几何误差。
2. **右键与副手冲突**：双刀格挡使用独立可重绑定键；保留右键旧居合。普通左键既可能攻击也可能挖掘，需要避免原版攻击和自定义攻击同时命中一次。不得全局取消交互事件。
3. **精准格挡时序**：服务端决定窗口与来袭方向，先支持可识别的普通近战；环境伤害、持续伤害、爆炸、魔法和任意模组伤害不能默认都可格挡。原版格挡/护甲事件先后顺序要查本机 API，不要通过事后回血伪装取消致死伤害。
4. **网络下的公平反馈**：第一人称可以预测姿态，但伤害必须等服务器；预测被拒绝时柔和恢复。不能用不受限回滚给高延迟客户端无限格挡窗口。首版明确可接受延迟与补偿上限，再实测。
5. **位移安全**：主角色移动使用服务器碰撞，影步不能直接 teleport 到光标/目标背后；墙角、半砖、台阶、坑边、坐骑/鞘翅状态分别检查。
6. **奥义镜头恢复**：开启界面、死亡、重生、切世界、手动切相机、目标消失都会中断。保存的是本次接管时的镜头状态；不能结束时一律强制第一人称，也不能持续覆盖用户已经手动改过的视角。
7. **强制终结兼容**：保留旧刀既有策略和测试，不声称可绕过所有外部 Boss 脚本。新动作的击杀/掉落统计在服务端死亡确认后提交，避免一次死亡发两次奖励。
8. **主世界配方格式**：已从本机 26.3 JAR 读取 `data/minecraft/recipe/iron_sword.json`：key 值是物品字符串/`#标签`，result 用 `id`。同版本配方书 `recipe_unlocked` 条件用 `recipes`。草案已准备在 draft-data，注册脇差前不得整体复制进正式资源，否则未注册的输出可能破坏加载。
9. **成就不能猜动作**：以实际接受的动作、有效伤害、格挡结果、死亡确认和资源提交构建事件，不能拿客户端粒子次数当命中次数。

## 独立分类的接入位置

当前 `Oborokage.onInitialize` 使用 `CreativeModeTabEvents.MODIFY_OUTPUT_ALL` 向原版 COMBAT prepend 太刀。后续按用户新要求移除此展示注册，新增本模组独立 `oborokage:equipment` 创造标签，顺序为太刀、脇差。不要删除原物品注册。搜索栏继续包含两把刀。

旧检查中“太刀在原版战斗栏第一格”应更新为“胧影标签存在、图标正确、顺序正确、搜索包含两刀、原版战斗栏不重复插入”。这是明确的 UI 要求变更，不属于允许改动战斗数值。

10 项成就统一进入剑录页面，旧 moon_still_hangs 仅改 parent，保留 ID 与条件；用临时存档验证既有解锁迁移及新玩家页面可见性。根节点“初见胧月”本身包含在 10 项成就中；老玩家登录时根据真实已有武器或旧成就补足根节点，避免页面不可见。

## 最低验收与迁移顺序

- 先记录旧太刀的 40/4 tick、1000+终结、12 格、18/45 冷却、2/8 消耗、4096 耐久及近战注册属性，做非削弱回归。既有 20/12 条检查作为旧证据，不代表新代码已通过。
- 旧单刀、双刀模式中的原版居合、装备切换后三种情况下都要确认原能力不受剑意/新增冷却限制。
- 两把刀在普通主世界工作台真实合成：摆放、配方书、shift 合成、材料扣除、物品组件/满耐久和数据包加载。
- 左右利手、主副手独立持握/挥动、第一/第三人称、狭窄室内与碰墙；关镜头/震动也可完整使用。
- 攻击不重复、每把刀耐久正确、取消/断线/换维度不幽灵攻击、不复制物品或剑意。
- 格挡正/侧/背面与窗口边界；普通防御和精准防御分别测。成就正例、负例和重复事件测试。
- 至少两客户端：攻击者、受击者/旁观者看到相同动作顺序；玩家保护默认保持。
- 先隔离实例与临时世界，再决定安装。保留同一 Mod ID，仅一份启用 JAR；构建、测试与安装哈希一致。
